# School Admission backend (M1–M6)

The backend is a single ASP.NET Core Web API targeting .NET 10, with an xUnit
integration test project. Future modules will live within the API project.

## Full-stack Docker deployment

From the repository root, run `docker compose up --build -d`. The API is available
at `http://localhost:8080`; Nginx also exposes it at `http://localhost:8088/api`.
See the [root README](../README.md) for setup, test commands and volume-preserving
shutdown. Stop a separately running development API before binding port 8080.

The backend Dockerfile builds a published API and an EF migration bundle. Compose
runs the bundle once after PostgreSQL becomes healthy and starts the API/worker
only after migration succeeds. Existing migration history makes reruns safe;
failed initialization blocks API startup. Runtime credentials come from the
environment. The API itself still never applies migrations at startup.

The full-stack project uses its own named volume. `compose.db.yml` remains the
separate development/test configuration below. Neither workflow resets or deletes
existing volumes. `/health` remains liveness; Docker additionally checks read-only
`/classes` for database/schema readiness.

From Git Bash:

```bash
cd backend
dotnet restore SchoolAdmission.sln
dotnet build SchoolAdmission.sln --no-restore
dotnet test SchoolAdmission.sln --no-build

cd SchoolAdmission.Api
ASPNETCORE_URLS=http://localhost:8080 dotnet run --no-launch-profile
```

In a second terminal:

```bash
curl -i http://localhost:8080/health
```

The liveness endpoint is controller-based `GET /health`, returning HTTP 200 with
`{"status":"healthy"}`. Class creation and read endpoints are described below.

Configuration uses standard ASP.NET Core providers, including environment variables:

- `ASPNETCORE_URLS` sets the listening address; no port is hard-coded.
- `HOLD_DURATION_SECONDS` defaults to `600` when absent. Startup fails if the value
  cannot be parsed as a positive 32-bit integer. New seat holds expire this many
  seconds after their server UTC decision timestamp.
- `ConnectionStrings__DefaultConnection` configures `AppDbContext`. Its committed
  value remains empty. A missing value only fails when a context is requested;
  `/health` stays a liveness check and does not test database readiness.
  Keep real credentials out of source control.

## M2 local PostgreSQL and migrations

Requires .NET 10 and Docker Desktop running Linux containers with Compose.
`compose.db.yml` runs only local PostgreSQL, not the final application stack.
The credentials below are deliberately non-production examples. Dev and test use
separate servers, database names, loopback ports, and named volumes.

From Git Bash in `backend/`:

```bash
docker compose -f compose.db.yml up -d --wait
dotnet tool restore
dotnet restore SchoolAdmission.sln
dotnet build SchoolAdmission.sln --no-restore

export ConnectionStrings__DefaultConnection='Host=127.0.0.1;Port=5432;Database=school_admission;Username=school_admission_dev;Password=local_m2_only'
dotnet ef database update --project SchoolAdmission.Api --startup-project SchoolAdmission.Api

# Offline migration checks (no PostgreSQL connection needed):
dotnet ef migrations has-pending-model-changes --project SchoolAdmission.Api --startup-project SchoolAdmission.Api
dotnet ef migrations script --project SchoolAdmission.Api --startup-project SchoolAdmission.Api
```

Initial migration: `20261110133159_InitialDatabase`. Migration SQL is generated by
EF Core 10.0.14 with Npgsql EF provider 10.0.3. All Microsoft EF packages and the
local `dotnet-ef` tool are pinned to 10.0.14. The API never applies migrations at
startup. UUIDs are generated in .NET; callers must supply UTC timestamps.

## M3 class management APIs

Configure `ConnectionStrings__DefaultConnection` and apply the existing migration
as above, then start the API:

```bash
cd SchoolAdmission.Api
ASPNETCORE_URLS=http://localhost:8080 dotnet run --no-launch-profile
```

In another terminal, create a class:

```bash
curl -i http://localhost:8080/classes \
  -H 'Content-Type: application/json' \
  -d '{"name":"Class 6 - Morning Shift","totalSeats":120}'
```

Returns `201 Created`, a `Location` header for the new class, and JSON such as:

```json
{"id":"019a69d3-1c00-7000-8000-000000000001","name":"Class 6 - Morning Shift","totalSeats":120}
```

IDs are UUID strings. Use the returned ID or Location for a detail request:

```bash
curl -i http://localhost:8080/classes
curl -i http://localhost:8080/classes/019a69d3-1c00-7000-8000-000000000001
```

Both GET routes return `200 OK`. The list is an array ordered by name with an ID
tie-breaker, or `[]` when empty. A detail response, or one list item, looks like:

```json
{
  "id":"019a69d3-1c00-7000-8000-000000000001",
  "name":"Class 6 - Morning Shift",
  "totalSeats":120,
  "heldSeats":0,
  "confirmedSeats":0,
  "availableSeats":120
}
```

POST trims surrounding name whitespace before validation and storage. Name must
be nonblank and at most 150 characters after trimming. `totalSeats` must be a JSON
integer from 1 to 2147483647; missing, null, fractional, quoted, or out-of-range
values are rejected. Invalid input or malformed JSON returns `400` with an
`application/problem+json` validation response and field errors. A malformed
UUID in the detail route returns `400`; a well-formed but unknown UUID returns
`404`. Names already present, including case differences or surrounding
whitespace, return `409` with a ProblemDetails title:
`A class with this name already exists.` The existing PostgreSQL unique index
enforces this even for racing inserts; only its specific `23505` violation is
caught. Other database exceptions retain normal error handling.

Each GET captures one UTC time and executes one no-tracking, server-side aggregate
query. HELD rows count only when `ExpiresAt > now`; CONFIRMED rows always count.
EXPIRED, CANCELLED, and stale HELD rows do not consume seats. Available seats are
`max(0, totalSeats - heldSeats - confirmedSeats)`. Raw held/confirmed counts remain
visible if seeded data exceeds capacity. GET never changes statuses. M4 hold
creation enforces capacity as described below; no cached counters are stored.

## M4 seat hold creation

After creating a class, use its UUID to request a hold. No JSON body is required:

```bash
curl -i -X POST http://localhost:8080/classes/019a69d3-1c00-7000-8000-000000000001/holds \
  -H 'X-Student-Id: 20152691234567890'
```

Returns `201 Created` after the database transaction commits, with JSON such as:

```json
{
  "holdId":"019a69d3-1c00-7000-8000-000000000002",
  "classId":"019a69d3-1c00-7000-8000-000000000001",
  "studentId":"20152691234567890",
  "status":"HELD",
  "expiresAt":"2026-11-10T14:10:00Z"
}
```

`X-Student-Id` must be a single header value containing exactly 17 ASCII digits.
It is stored directly as a string, preserving leading zeroes. Missing, blank,
non-digit, Unicode-digit, whitespace-padded, short, long, and multiple values
return `400` with a validation problem. A malformed class UUID returns `400`;
a well-formed UUID without a class returns `404`. Full classes and duplicate
active student/class applications return `409` with a useful ProblemDetails
title. A live HELD or any CONFIRMED row blocks duplicates; requests never extend
existing holds or overwrite confirmed admissions. Only `23505` for the known
active-application unique index is mapped to a duplicate conflict; unrelated
database errors retain normal error handling.

The allocation critical section uses PostgreSQL, so it also protects requests
handled by separate API instances:

1. Begin an explicit READ COMMITTED transaction.
2. Execute parameterized `SELECT * FROM "AdmissionClasses" WHERE "Id" = @id FOR UPDATE`.
   Materialize this targeted query directly to avoid EF composition over the lock SQL.
3. After acquiring the class-row lock, capture one fresh `DateTime.UtcNow`.
4. Set the requesting student's elapsed HELD rows (`ExpiresAt <= decisionUtc`) to
   EXPIRED with an immediate database update in this transaction. This frees the
   partial unique index before a replacement insert, preserving the history rows.
5. Check live duplicates and count effective HELD plus CONFIRMED rows while the
   class lock is held. Other students' stale HELD rows are ignored for capacity
   without changing their status. EXPIRED and CANCELLED rows do not count.
6. If capacity remains, insert HELD with CreatedAt equal to decisionUtc and
   ExpiresAt equal to decisionUtc plus the validated duration, then commit before
   returning 201. ExpiresAt is stored as timestamptz and returned in UTC.

Requests for the same class serialize at the row lock. In READ COMMITTED, hold
queries after that lock see the preceding winner's committed insert. Different
class rows can be locked independently. The existing partial unique index remains
additional duplicate protection. All failure/conflict paths dispose the
uncommitted transaction, rolling back expiry normalization and any insert and
releasing the lock. No in-memory lock or seat counters are used.

M5 lifecycle operations and the M6 expiration worker follow the same class-first
lock order, as described below.

## M5 hold lifecycle APIs

Use the UUID returned by hold creation. All examples below use an illustrative ID.

```bash
# Public lookup: no X-Student-Id header is required.
curl -i http://localhost:8080/holds/019a69d3-1c00-7000-8000-000000000002
```

Returns `200` with exactly these fields; it does not disclose the student ID:

```json
{"holdId":"019a69d3-1c00-7000-8000-000000000002","classId":"019a69d3-1c00-7000-8000-000000000001","status":"HELD","expiresAt":"2026-11-10T14:10:00Z"}
```

```bash
curl -i -X POST http://localhost:8080/holds/019a69d3-1c00-7000-8000-000000000002/confirm \
  -H 'X-Student-Id: 20152691234567890'
```

An owner confirming a live HELD admission receives `200`:

```json
{"holdId":"019a69d3-1c00-7000-8000-000000000002","status":"CONFIRMED"}
```

Owner retries of CONFIRMED records return the same response, including when the
original expiry timestamp has elapsed. ConfirmedAt is set only on the initial
transition; retries never extend ExpiresAt or increase occupied seats. EXPIRED,
CANCELLED, and elapsed HELD records return `409`; elapsed HELD is persisted as
EXPIRED and never confirmed.

```bash
curl -i -X DELETE http://localhost:8080/holds/019a69d3-1c00-7000-8000-000000000002 \
  -H 'X-Student-Id: 20152691234567890'
```

Cancellation of owned HELD or CONFIRMED admissions returns `204` with no body,
marks only that UUID CANCELLED, and sets CancelledAt. It releases the seat without
deleting the historical row or clearing ConfirmedAt. Repeated owner cancellation
returns `204` without changing timestamps. Cancelling an EXPIRED record returns
`409`; an elapsed HELD record is first persisted as EXPIRED, then returns `409`.
Cancelling an older UUID never cancels a later replacement for the same student.

```bash
curl -i http://localhost:8080/me/holds \
  -H 'X-Student-Id: 20152691234567890'
```

Returns `200` with only the requesting student's current and historical records,
ordered by CreatedAt descending then UUID ascending, or `[]` when none exist:

```json
[
  {"holdId":"019a69d3-1c00-7000-8000-000000000002","classId":"019a69d3-1c00-7000-8000-000000000001","className":"Class 6 - Morning Shift","status":"CONFIRMED","expiresAt":"2026-11-10T14:10:00Z"}
]
```

Confirm, cancel, and My Holds require the same single, exactly 17 ASCII digit
`X-Student-Id` header as creation. Missing, malformed, whitespace-padded, Unicode,
and multiple values return `400`. Malformed hold UUIDs return `400`; unknown UUIDs
return `404`. Ownership mismatches on confirm/cancel also return `404` with no
student information and no state change, including for stale records.

Lifecycle operations use READ COMMITTED transactions. They first resolve only
the hold's class UUID, lock the class row using the shared parameterized
`SELECT ... FOR UPDATE` helper, then lock and reread the targeted hold row. No
tracked hold is loaded before waiting. Decisions use fresh UTC time after both
locks, matching M4's class-first order and serializing against reservations.
Success and any deliberate expiry normalization commit before responses. Other
failure paths roll back on transaction disposal. Confirmation moves one occupied
seat from HELD to CONFIRMED; cancellation releases it. No counters are stored.

Public hold GET safely persists expiry of its targeted stale HELD record under
these locks, without changing terminal states or unrelated records. My Holds
uses one no-tracking projection/join for class names and effective status; it
does not write or lock multiple classes. It reports EXPIRED when HELD and
ExpiresAt <= its captured UTC time. Class GET endpoints remain read-only.

### Prototype assumptions for later ASSUMPTIONS.md

- Public hold lookup without a student header follows the assignment contract.
  A UUID acts as a lookup token; this is not strong authentication. The response
  omits StudentId, but a known UUID reveals class, status, and expiry.
- Header-only identification is not proof of identity. Ownership checks prevent
  writes with a different header value; stronger authentication is outside this
  prototype's specification. My Holds filters by that provided identity.
- Cancellation is allowed for both HELD and CONFIRMED admissions in this
  prototype. EXPIRED cancellation returns 409; CANCELLED retries return 204.
- Expiry wins over late confirmation. Confirmed admissions never expire based
  on the original hold timestamp.
- Confirmation represents the workflow's verified-fee step. No actual payment
  verification or gateway is implemented.
- M6 handles background expiry persistence. Request-time expiry checks remain
  necessary because persistence is eventual and the database may be unavailable.

## M6 automatic hold expiration

`HoldExpirationWorker` is registered as an ASP.NET Core `BackgroundService` and
starts automatically with the API, even when no HTTP requests arrive. Each cycle
creates and asynchronously disposes a new DI scope, scoped `HoldExpirationSweep`,
and `AppDbContext`. `TimeProvider.System` supplies UTC timestamps in normal use.
No singleton captures a scoped context, and no startup migration is performed.

Set the polling interval through standard ASP.NET Core configuration:

```bash
export HOLD_EXPIRATION_POLL_SECONDS=5
```

The default is 5 seconds. Values must be integers from 1 through 4294967 seconds,
the largest whole-second interval supported by the .NET delay timer. Missing
configuration uses the default; zero, negative, non-integer, overflowing, and
unsupported timer intervals fail startup with feedback naming the setting.
`HOLD_DURATION_SECONDS` still controls new-hold duration and is unchanged.

The first sweep runs on worker startup. The configured delay occurs after each
completed or failed cycle, so cycles do not overlap or spin on database errors.
For each sweep:

1. Discover at most 256 class IDs from the oldest elapsed HELD records using a
   non-locking, no-tracking scalar query. The existing `(Status, ExpiresAt)` index
   supports the status/time range and expiry ordering.
2. Process at most 32 distinct classes, one READ COMMITTED transaction per class.
   Acquire that class row using the existing parameterized `FOR UPDATE` helper.
3. Capture a fresh UTC decision time after acquiring the lock. Update at most 256
   elapsed HELD records for that class using one set-based `ExecuteUpdateAsync`.
   Status and `ExpiresAt <= decisionUtc` are rechecked in the update predicate;
   discovery can be stale. No hold rows are locked before the parent class row.
4. Change only Status to EXPIRED and commit. Preserve all IDs, timestamps, student
   numbers, and history. Future HELD, CONFIRMED, CANCELLED, and already EXPIRED
   records are untouched. Remaining backlog is handled by later sweeps.

The class-first critical section serializes with M4 reservations, M5 lifecycle
writes, and other worker instances. Repeated sweeps are idempotent. Transactions
are released before moving to another class. A cycle error may follow earlier
classes' successful commits; the next cycle safely resumes from current state.

Shutdown cancels timer waits and database operations. Disposing an uncommitted
transaction rolls back its updates and releases locks. Failed cycles log an Error
event containing exception type and PostgreSQL SQLSTATE when available, then
retry with a new scope after the polling delay. Raw exception messages, student
IDs, and connection strings are not included in worker diagnostics. Every failed
cycle is logged, including persistent failures; check connection configuration,
explicit migration setup, and database availability when these events recur.
Database failure does not deliberately stop the API; `/health` remains liveness.

Persisted EXPIRED status is eventual: polling, backlog, and lock waits affect its
timing. All existing API expiry/capacity checks are retained, so an elapsed HELD
record does not consume capacity even before a sweep persists its status. No
redundant counters, new endpoints, schema changes, or external scheduler are used.

## Real PostgreSQL tests

```bash
# Safe without PostgreSQL: health runs; unconfigured database tests report SKIP.
dotnet test SchoolAdmission.sln --no-build

# Explicitly enable database tests against the separate local test server:
export SCHOOL_ADMISSION_TEST_CONNECTION='Host=127.0.0.1;Port=5433;Database=school_admission_m2_tests;Username=school_admission_test;Password=local_m2_test_only;Timeout=5'
dotnet test SchoolAdmission.sln --no-build --filter 'Category=PostgreSQL' --logger 'console;verbosity=normal'

# Run health and database tests together once configured:
dotnet test SchoolAdmission.sln --no-build
```

Tests only accept the exact database name `school_admission_m2_tests`. They apply
the checked-in migration to that dedicated database. M2/M3 tests use rollback
transactions; M4 tests use real commits and scoped cleanup as described below.
No `EnsureDeleted`, database drop, SQLite, or EF InMemory provider is used. Use
this database exclusively for tests. If a connection is supplied and PostgreSQL
is unreachable, tests fail instead of silently skipping.

The M3 HTTP tests use `WebApplicationFactory<Program>` and the existing guarded
PostgreSQL fixture. Each test's HTTP request contexts share its PostgreSQL
transaction and connection; requests are sequential within the test. Initial
deletes give list tests an empty view inside that transaction. All deletes,
seeding, and HTTP writes roll back on disposal, preserving persistent records.
Tests within the HTTP test class run sequentially; existing schema tests retain
their own isolated transactions. No normal development database is used.

Run only M3 HTTP tests with:

```bash
dotnet test SchoolAdmission.sln --no-build --filter 'FullyQualifiedName~ClassEndpointsTests'
```

These tests cover creation/persistence/Location, name and seat validation,
case-insensitive conflicts, ordered/empty lists, UUID errors, effective counts
across multiple classes, stale HELD rows, read-only behavior, and over-capacity
display. Query interception verifies one database read per GET.

Run only M4 HTTP tests with:

```bash
dotnet test SchoolAdmission.sln --no-build --filter 'FullyQualifiedName~HoldEndpointsTests' --logger 'console;verbosity=detailed'
```

M4 uses the same fixture/database-name safety guard, independent physical
PostgreSQL connections, production API DI, committed seed rows and HTTP writes,
and fresh connections to verify committed state. Each test creates unique class
UUIDs and deletes only its own holds/classes on disposal, child rows first. No
outer rollback transaction hides writes from competing HTTP requests. The M4
collection runs separately from other test collections so M3 empty-list tests
cannot interfere with committed test records; requests within each contention
test run concurrently across two independent API hosts.

Contention tests use a real start barrier, hold the target row with a separate
PostgreSQL transaction, then observe every competing request waiting in
`pg_stat_activity` before releasing the blocker. Explicit deadlines bound waits.
The cases cover 24 students/1 seat, 40 students/5 seats, 24 students/5 seats with
2 confirmed admissions, and 24 same-student requests with/without stale history.
They assert exact 201/409 counts and committed occupancy, not just responses. A
separate test proves another class can commit while the first class is locked,
and verifies the waiting request's decision timestamp is after lock release.
Tests also cover headers, TTL/default options binding, full/duplicate conflicts,
history preservation, stale reapplication, and rollback of normalization on 409.

Run the M5 tests with:

```bash
dotnet test SchoolAdmission.sln --no-build --filter 'FullyQualifiedName~HoldLifecycle' --logger 'console;verbosity=detailed'
```

M5 reuses the guarded committed-data scope and isolated test collection from M4.
Contract cases cover exact JSON fields, missing/malformed/multiple headers,
ownership, expiry, idempotent retries, cancellation of confirmed admissions,
replacement history, student isolation, ordering, and a one-query My Holds read.
Concurrency cases use independent physical connections and two API hosts,
observe every competing request waiting for an actual PostgreSQL class-row lock,
and verify committed rows and class availability. Cases include repeated
confirm/cancel requests, confirm versus cancel, cancellation versus reservations,
late confirmation versus reapplication, and expiry-normalizing GET versus late
confirmation. Lock-wait tests also alter the committed hold while a confirmation
waits, proving that it rereads current state and captures time after the wait.

Run the M6 tests with:

```bash
dotnet test SchoolAdmission.sln --no-build --filter 'FullyQualifiedName~HoldExpiration' --logger 'console;verbosity=detailed'
```

Existing API test hosts explicitly remove only the expiration hosted-service
registration to preserve their fixtures' controlled history. M6 tests start the
real DI-registered worker in separate API hosts and verify commits through fresh
independent PostgreSQL reads. No HTTP request is made before proving automatic
expiry. A controlled UTC `TimeProvider` supplements live PostgreSQL for exact
boundaries; eventual assertions observe database state instead of relying on
long sleeps.

M6 uses the guarded dedicated test database and the non-parallel committed-hold
collection. Before seeding, its tests require that database to contain no holds;
they fail without starting a worker if unrelated/leftover holds exist. Cleanup
still deletes only test-owned class UUIDs and their records. No volumes or
databases are reset. These safeguards prevent a global worker from expiring other
tests' data.

Coverage includes no-request persistence, future/terminal status preservation,
exact UTC boundary, bounded batches, repeated sweeps/restarts, current-state
rechecks after lock waits, fresh decision time, and cancellation during timer/
lock waits and after an update but before commit. An actual closed-port connection
failure tests logging, liveness, new context creation, and recovery on later
sweeps. Contention tests observe one/two live workers and simultaneous HTTP
reservation/confirmation/cancellation requests waiting in PostgreSQL, then verify
committed statuses, retained history, exact expiration counts, and capacity.

The PostgreSQL suite checks valid persistence, all active-status duplicate pairs,
expired/cancelled history, malformed birth-registration numbers, seat counts,
status validation, case-insensitive class names, foreign keys, column types,
nullability, and index definitions. Missing database configuration produces
explicit skips, which do not constitute database verification.
